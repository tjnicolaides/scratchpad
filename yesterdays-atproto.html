MVP Design Brief · AT Protocol · Grug-brained

Yesterdays,
rebuilt on atproto

Crowdsourced placement of historical photos onto a map — but every guess is a record the contributor owns, not a row you moderate.

point-or-area guesses consensus, not accept/reject social distribution one new moving part: the AppView

The whole design turns on one inversion: Yesterdays keeps a central table and an admin picks the one true location per photo. We keep every guess as a user-owned atproto record and let a read-only indexer turn the pile of guesses into a confidence surface. Nobody's contribution is ever rejected — it's weighed.

The honest cost

Almost everything here is a normal web app: a static single-page app, images hotlinked from source archives, records written to PDSes you don't run. The one genuinely new operational component is the AppView — an indexer that reads records out of atproto, stores geometry, computes consensus, and serves the map. That's a database plus a long-running worker you have to keep alive. Everything else you can lean on existing infra for. We do not build a PDS or a relay.

01 Lexicon schemas

Two record types. One is optional.

A contribution is a georef record in the contributor's own repo. Its location is a discriminated union: a point (a sharp vote) or an area (a soft "roughly here"). Photos are referenced by archive + item id, never by a central catalog id — so two people can georeference the same LOC photo without anything existing "in the middle" first.

Two atproto gotchas baked into the schema

Lexicon has no float type (floats break the canonical CBOR hashing that gives records their CIDs). So lat/lng are strings in decimal degrees — which also happens to match the emerging community.lexicon.location convention, so we're not inventing a wheel here. Radius is an integer in meters, which is fine as-is. Second: we deliberately start the location union at point + circle only. GeoJSON polygon is cut from the MVP — see the note after the schema.

The contribution record

place.yesterdays.georef
{
  "lexicon": 1,
  "id": "place.yesterdays.georef",
  "defs": {
    "main": {
      "type": "record",
      "key": "tid",          // one repo can hold many guesses
      "record": {
        "type": "object",
        "required": ["subject", "location", "createdAt"],
        "properties": {
          "subject":  { "type": "ref", "ref": "#subject" },
          "location": { "type": "union", "refs": ["#point", "#circle"] },
          "confidence": { "type": "string", "knownValues": ["sure", "guess"] },
          "note":  { "type": "string", "maxGraphemes": 300 },
          "createdAt": { "type": "string", "format": "datetime" }
        }
      }
    },

    "subject": {                       // which photo — by external archive id
      "type": "object",
      "required": ["archive", "itemId"],
      "properties": {
        "archive":      { "type": "string", "maxLength": 128 },  // "loc", "lva", "valentine"
        "itemId":       { "type": "string", "maxLength": 512 },  // stable id WITHIN that archive
        "iiifManifest": { "type": "string", "format": "uri" },
        "sourceUrl":    { "type": "string", "format": "uri" }
      }
    },

    "point": {                          // a sharp vote: "it was HERE"
      "type": "object",
      "required": ["lat", "lng"],
      "properties": {
        "lat":        { "type": "string" },   // decimal degrees, WGS84, as string
        "lng":        { "type": "string" },
        "bearingDeg": { "type": "integer", "minimum": 0, "maximum": 359 } // optional camera facing
      }
    },

    "circle": {                         // a soft constraint: "somewhere around here"
      "type": "object",
      "required": ["lat", "lng", "radiusMeters"],
      "properties": {
        "lat":          { "type": "string" },       // center
        "lng":          { "type": "string" },
        "radiusMeters": { "type": "integer", "minimum": 1, "maximum": 50000 }
      }
    }
  }
}

Field rationale

FieldTypeWhy it's shaped this way
subject.archive + itemIdstringThe join key. No central photo table — the pair is the photo's identity. archive is a short registry key so the indexer knows how to build a canonical IIIF URL if one isn't supplied.
subject.iiifManifesturi?Optional. Lets a contributor pin the exact IIIF source so the app can render tiles straight from the archive — same "serve by reference, store no pixels" stance as Yesterdays.
locationunionThe core discriminated union. #point = sharp vote; #circle = soft area. The $type on the value tells the indexer which one it got.
point.lat / lngstringDecimal degrees as strings (no lexicon float). Parse to float only inside the indexer.
point.bearingDeginteger?Camera facing, 0–359° from true north. Cheap to store, powers a "which way was the camera pointing" arrow later. Optional — never force it.
circle.radiusMetersintegerHow rough the guess is. This number literally becomes the "softness" weight in consensus — a 3km circle counts for far less than a 40m one.
confidenceenum?Self-reported sure / guess. A light thumb on the scale; the geometry does most of the work.
createdAtdatetimeStandard. Also lets the indexer take "latest wins" if one person revises their own guess.
Over-engineering flag — cut from v1

GeoJSON polygon. It's tempting to "lean on the GeoJSON standard," but GeoJSON can't even express a circle, and its [lng, lat] ordering is a classic footgun against everyone's lat, lng habit. A circle (center + radius) covers the entire "I only know the neighborhood" case with two numbers. Add a #polygon ref to the union later only when a real contributor hits a shape a circle can't honestly express (a long riverfront, an L-shaped block). It slots in as a third union member with zero migration — so there's no cost to waiting.

The photo-enrichment record — optional

Since there's no central catalog, title/date/description also have to live somewhere ownable. A second record type lets anyone annotate a photo, keyed by the same subject. The indexer merges these the same way it merges guesses. Skip it entirely in the walking skeleton.

Namespace note: place.yesterdays.* is a placeholder. A real NSID needs a domain you actually control (reverse-DNS). Before writing anything to production PDSes, also check whether community.lexicon.location.* is far enough along to reuse for the geometry defs rather than minting your own.

02 What runs, and what talks to what

Four things you build, three you borrow

Follow a single guess from the moment a contributor drops a pin to the moment it shows up on someone else's map. The only box with a heavy border is the only thing that's operationally new.

Over-engineering flag — how the AppView ingests

The brief says "backfill by polling PDSes." Be careful: you can't poll all PDSes — there's no such list — you can only poll repos you already know about. So polling needs a seed set of contributor handles, which is fine early (you'll know your first users) but doesn't discover strangers. The honest pragmatic answer is Jetstream — a filtered, JSON firehose someone else already runs — subscribed to just our two record types. It's less code than a robust poller and it does discover new contributors. So: poll a seed list for the skeleton; move to Jetstream the moment you want open contribution. Running your own relay/firehose stays off the table.

03 Consensus, in plain terms

Every guess is a weight, not a vote you count

Think of each contribution as dropping weight onto the map. A point drops a tall, narrow pile — it's confident and specific. A circle spreads the same amount of weight thinly across its whole area — a 40m circle is a modest hill, a 3km circle is barely a smudge. Where piles stack up, confidence rises. Where they don't, it stays honest and low.

The MVP algorithm (deliberately not a KDE)

  1. Gather all current georef records for a photo (one per contributor — latest createdAt wins if someone revised).
  2. Cluster the points by proximity — a simple distance threshold (say ~75m in a city) is enough; DBSCAN if you want to be fancy, but you don't need to be yet.
  3. Fold in the areas as soft support. A circle doesn't create a cluster on its own; it boosts a point-cluster whose center falls inside it, and the boost is bigger for tighter circles. Areas with no points inside them become a faint fallback region shown only when there are no point clusters at all.
  4. Score each cluster: points in cluster + overlapping areas × small weight, penalized by how spread out the cluster is. Highest-scoring cluster centroid is the displayed location.
  5. Detect contest: if a second cluster scores within, say, 60% of the top one and sits well outside it, mark the photo contested and render both.

No grid, no gaussian math, nothing to tune blindly. It's explainable in a sentence to a contributor ("three people put it here, one drew a circle around it, so we're fairly sure"), which matters for trust.

What confidence a photo shows

High
≥3 agreeing contributions, tight spread, no rival cluster — or a couple of tight points sitting inside overlapping areas. Rendered as a solid pin.
Medium
2 agreeing points, or 1 point corroborated by an area it sits inside. A pin with a "needs a second opinion" hint.
Low
A single guess, or only wide areas and no points. Shown as a translucent area/blob, never a hard pin — the map should look unsure.
Contested
Two or more comparable clusters that don't reconcile. Both drawn, both labeled, plus a "locations disagree" chip. Disagreement is content, not an error.
Over-engineering flag — cut from v1

A real kernel-density confidence surface / heatmap. It looks great in a demo and it's the "right" model of a probability field, but it needs a grid, a bandwidth parameter you'll fiddle with forever, and tiles to serve it. Clustering gives you the same three answers a user cares about — where, how sure, and is it contested — with arithmetic. Build the heatmap in Phase 3 as a visual upgrade once you have enough real guesses to tune it against.

04 Phased build

Thinnest walking skeleton first

The skeleton's job is not to be useful — it's to prove the atproto write → index → read loop end to end with the least code. Everything valuable comes after that loop is real.

0

Walking skeleton — points only

One archive, a handful of hardcoded photos rendered via IIIF. Log in with OAuth, drop a point, write one georef record to your PDS. The AppView polls a seed list of a few known handles, stores raw points, and serves "all points for photo X." The map shows the raw dots — no consensus yet. If a dot you place shows up on a second browser, the architecture is proven.

Ships: lexicon (point only) · OAuth write · poller · Postgres · dumb read API · map

1

Areas + consensus

Add #circle to the union and a "draw a circle" tool. Add PostGIS and the clustering/scoring above. The map now renders confidence tiers, area overlays, and the contested state. This is the first version that's actually better than a spreadsheet of pins.

Ships: circle geometry · PostGIS · cluster + score · confidence rendering

2

The social loop

On a guess, optionally cross-post to Bluesky (an app.bsky.feed.post with a static map thumbnail and a link back). Add a leaderboard from indexed contributions and a GeoGuessr-style mode: show a photo, take a guess, score it against the current consensus. Switch ingestion from the seed-list poller to Jetstream so strangers can join.

Ships: Bluesky post · Jetstream ingest · leaderboard · guess-and-score mode

3

Earns-its-place later

Only if real usage demands them: GeoJSON polygons for shapes a circle can't honestly hold; a KDE heatmap surface; a labeler/blocklist for moderation; camera-bearing arrows; multi-archive support with a shared archive registry.

Deferred until a real contributor or number forces the issue

05 Open questions for a human

Decisions I shouldn't make alone

R1Moderation without deletion

You can't delete someone else's record — it lives in their repo. The AppView can only refuse to index spam, slurs, or troll guesses. That's a labeler/blocklist story, and it's a real one the moment contribution is open. Who runs it, and by what policy?

Leaning AppView-side allow/deny list for the skeleton; a proper atproto labeler in Phase 2+.

R2Consensus gaming via the social loop

Leaderboards reward volume, and volume can move consensus. One motivated person with three accounts can manufacture a "high-confidence" cluster. How much Sybil resistance is worth building before launch vs. accepting it for an MVP among a friendly early community?

Leaning weight by distinct account age/reputation later; accept the risk in the skeleton.

R3The archive registry & photo identity

Everything hinges on archive + itemId being stable and canonical. Who governs the list of archive keys? What happens when the same photo exists in two archives — are those one photo or two? Do we trust contributor-supplied IIIF URLs or resolve them ourselves?

Leaning a small hand-curated registry we control; treat cross-archive dedupe as out of scope for v1.

R4Lat/lng encoding — commit before writing anything

Strings (chosen here) vs. fixed-point integers (e.g. microdegrees). Strings are readable and match community.lexicon; integers are unambiguous but need a documented scale. This is a one-way door once records exist in the wild.

Leaning strings, aligned to the community lexicon — but confirm that lexicon's direction first.

R5Licensing & image rights

Yesterdays is AGPLv3 — do we clean-room or inherit its obligations? And IIIF hotlinking has per-archive terms; some archives may not want their tiles embedded in a gamified app. Worth a check with the archives before the social loop amplifies traffic.

Leaning clean-room the code; get explicit OK from at least one archive before Phase 2.

R6Confidence thresholds are guesses

The "≥3 = high," "75m cluster radius," "60% = contested" numbers are placeholders. They can only be tuned against real contribution patterns, which we won't have until the skeleton is live. Plan to revisit them, and don't over-promise accuracy early.

Leaning ship the placeholders, instrument them, tune in Phase 1 with real data.
